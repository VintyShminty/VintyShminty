# 2026-10-18

Branch: `fix/search-matching`

## What was done
- Fixed the item search so a brand like H&M no longer brings up unrelated items. Eden searched "H&M" on the live site and got Tommy Hilfiger jeans and Puma shoes. The search was cutting "H&M" into the two letters "h" and "m" and accepting any item whose title or brand had those letters anywhere. Now a word keeps the marks that join it (H&M, Levi's, T-shirt, ג'ינס), the spellings with and without the mark find the same items (HM, levis, גינס), and a word of one or two letters only matches a whole word. Recorded as D-057 in `docs/design.md`.
- A whole search that only looks like a brand (a typo such as "nikee" or "zaraa") still becomes that brand, but a brand plus any extra word ("nike air", "zara xs", "תיק zara") no longer collapses into the brand alone.
- In the default order, items with every search word at the start of a word in the title or brand now come before items where the word hides inside a longer word. Searching גינס used to show a book by "היגינס" first.
- Favourites search uses the same matching as the main search.
- Tests: a new unit test file for the word splitting and new live database tests for H&M, Levi's, Hebrew geresh, single letters and the brand typo rule. 167 server search tests pass, typecheck and lint are green.
- Checked against real data: a helper ran 244 real searches (taken from the 196 live listings) against the live server and against the fixed server running on a read-only copy of those listings. Production got 43 of them wrong (junk for H&M and single letters, missing results for גינס, זקט, Hebrew prefixes, "גינס קצר", "pullbear", "sacks", brand plus word searches). The fixed code matched the expected answer on every one after the last change.

## Decisions
- D-057 (Eden asked for a battle tested search, Claude proposed the rules): search words stay whole, short words match whole words only, word-start matches rank first, a brand typo needs the same number of words. In `docs/design.md`.

## Problems and fixes
- The first fix was written on top of an old copy of the search code (the main folder had uncommitted work and an older file). Redone on a fresh copy of main in a separate folder (`../VintyShminty-search`). Lesson: start from a clean worktree before reading code.
- The Browser pane's dev server always starts from the main folder, not the worktree, so the fix seemed to do nothing. Started the server and website by hand from the worktree instead.
- Copying the live database directly was blocked by the safety rules, so the 196 live listings were pulled through the public API into a separate local database (`vinty_live_copy`, no photos). That copy is only for testing and is not part of the repo.
- One unrelated server test (a seeded member's listing photos) fails on this machine because the local sample data has changed. Not touched.

## Open questions

- "cheapest nike" (two words) does not go to the plain words helper, because that needs three words or a number (D-037). Suggested default: leave it.

## Afternoon: Face ID only for logging in, a database outage and the data drain

Branches: `fix/face-id-login`, `fix/face-id-permission-text`, `fix/fewer-server-starts` (all merged), this entry on `docs/log-2026-10-18-faceid`

### What was done

- **No more Face ID on every open (#129).** A signed in person now goes straight into the app. Sign in already lasts 30 days and renews every day the app is used, so a regular user never logs in again.
- **Face ID helps you log in instead.** After someone with an account logs in with their password, the app offers to keep the email and password in the phone's keychain (the iPhone's locked safe) behind Face ID. The login screen then shows Log in with Face ID. Brand new accounts (password, Google or Apple) are never asked. Settings, Sign in and safety has a Log in with Face ID switch. If the saved password stops working, the app forgets it and asks for the new one.
- **The old Face ID permission sentence is back for now (#130).** The new sentence ("to log you in") is part of the built app, so it stopped silent updates from reaching build 7. Change it again with the next Xcode build.
- **PR 126 conflict fixed.** Two versions of the 2026-10-17 diary both added sections at the end. Kept all four.
- **Home and search failed on the phone ("Something went wrong").** The live database (Neon) ran out of memory: about 110 open connections on its smallest size. The server copies on Vercel now open at most 2 connections each instead of 10 (the Vercel setting `DATABASE_POOL_MAX` is 2, server redeployed).
- **The data drain is fixed (#133).** Neon showed 80.8% of the monthly data transfer used in 5 days, for a database of about 8 MB. Cause: each Explore tile asked the server for its cover photos separately (20 to 50 requests at once, also on every website build), Vercel started a fresh server copy for many of them (265 in 30 minutes), and every fresh copy downloaded the category, size and fee lists (about 300 KB), then again every minute. Now one request brings every tile's covers for a side, Vercel's cache answers it for 5 minutes without starting the server, and the lists are kept 10 minutes.
- **Live everywhere.** Website and server went live on each merge. Two silent app updates went out this afternoon (both on build 7). The website Explore page was checked: every tile shows a real listing photo.

### Decisions

- Eden: Face ID is for logging in, not a lock when the app opens. Only for people who already have an account, and always optional. Recorded in `docs/knowledge/decisions.md` and `CLAUDE.md`.
- Eden: stay on Neon's free plan for now. Lower the server's connections and fix the data drain first. The database size stays at its smallest (letting it grow would use up the free 100 compute hours faster).

### Problems and fixes

- **Silent update blocked by one sentence.** The check before publishing showed the app's native fingerprint (the ID of the built part of the app) had changed, so phones on build 7 would ignore the update. Found the cause, the Face ID permission sentence, and put the old one back. Lesson: any change in `app.json` needs a new Xcode build, check the fingerprint before every update.
- **Out of memory at 12:25.** Same as last night's outage, but this time it lasted several minutes. Read the live server's error log, then looked (read only) at the database's open connections: 110 of a maximum of 112.
- **Main is far ahead of the old branch.** The Face ID change was written in the main folder, which sits on an old branch with unsaved work. Moved it onto a fresh copy of main and removed three newer spots that leaned on the old lock (a hidden photo viewer, the modal guard, the lock screen itself).
- **Neon numbers to watch.** The free plan's compute time is also high: 19.6 compute hours in 5 days, on track for about 117 of the 100 a month.

### Open questions

- Is the data transfer now slowing down? Check Neon's usage tomorrow. Suggested default: if it is still climbing fast, look for the next biggest reader.
- Compute hours may run past the free 100 this month. Suggested default: watch it, upgrade to Launch only when real users arrive.
